# 云端同步设计（离线优先）

> **状态（1.4）**：地基已落地 —— **接口层收敛**（`services/api.js`）+ **服务器地址可配置**
> （设置 › 关于 › 服务器地址，带测试连接）。
> **后端尚未接入**，所以现在所有同步调用都自动降级为纯本地，行为和接入前 100% 一致。
>
> **路线已定（2026-10-13）**：面向**普通用户**，走「手动同步」，**不做 GitHub 登录**。
> 理由与备选方案见 §六。当前不做账号体系、不做增量同步、不做自动合并。

---

## 一、三条铁律

1. **本地永远是真相源。** App 必须在完全断网时独立跑完所有功能 —— 这是本项目的立身之本。
   同步只能是锦上添花，绝不能变成"没网就用不了"。
2. **不同步"状态"，同步"事实"。** 上传的是**逐条学习记录**（带时间戳），不是"当前掌握度快照"。
   快照合并是说不清的烂账；逐条事实可以重放、可以幂等重传。
3. **绝不静默丢数据。** 冲突自动按 `updatedAt` 取新；自动解决不了的才交用户决定，
   任何情况下都不允许"拉下来把本地盖了却不告诉用户"。

> ⚠️ 铁律 2（逐条事实）是**自动同步**路线才需要的。当前「手动同步」路线下
> 整份上传即可，**不改 `store.js`**，也就不用拆逐条记录 —— 见 §七 的说明。

## 二、分层与职责

| 层 | 位置 | 职责 | 不许做什么 |
|---|---|---|---|
| 业务层 | `pages/` `pkgStudy/` `components/` | 调用能力、展示结果 | **不许出现域名、不许直接发请求** |
| 接口层 | `services/api.js` | 拼地址、带 token、归一化错误、判定"还没接" | 不含业务逻辑 |
| 同步层 | `services/account-sync.ts` | 推拉数据、合并冲突、维护游标 | 不关心 UI |
| 传输层 | `services/http.js` | 超时、重试、熔断 | 不关心业务语义 |

契约：**业务层出网只能经过 `services/api.js`**（`_tools/check-api.js` 会扫）。

## 三、同步单元

| 数据 | 粒度 | 冲突键 | 备注 |
|---|---|---|---|
| 掌握度 | 一词一条 | `bookId:wordId` | 同步"这条记录"，不是整本词书 |
| 错题 | 一词一条 | `wordId` | 带 `addedAt` |
| 每日统计 | 一天一条 | `day` | 可重算，用 max 合并更稳 |
| 设置 | 整份 | 单一 | 小，整份覆盖即可 |
| 对话陪练 | 一会话一条 | `sessionId` | 体积大，按需拉取 |

> 手动同步路线下，这些**整包成一个加密文件**走（即现有 `backup.js` 的产物），
> 上表只在将来改增量同步时才用得上。

## 四、冲突解决

- 每条记录带 `updatedAt`（毫秒）；**同键取 `updatedAt` 大的**。
- 删除用**墓碑**（`deletedAt` 标记），不物理删 —— 否则"本地删了、远端还在"时
  一拉就复活，或者一推又把对端的删了。
- 时钟不可信：跨设备对不上时保守取值（掌握度取低、错题取并集），宁可不聪明也不能算错。

**手动同步路线下的简化**：冲突是低频事件（几天才可能撞一次），
**不做自动合并**，直接弹「以哪份为准」让用户选，并明确显示两份各自有多少条记录。
诚实、不会算错，也不需要 `updatedAt` 基建。

---

## 五、安全

- **强制 HTTPS**：`http://` 只允许本机调试放行，其余一律拒绝并提示。
- **token 不扩散**：只存本地；**不进备份导出、不进日志、不进 AI 上下文**。
- **返回值当不可信处理**：服务端返回什么都要能容错（缺字段、类型错、超长），
  前端必须能独立跑，绝不因服务端脏数据白屏。
- **同步码只用于派生密钥，不上传明文**（见 §八）：服务端存的是密文，
  它自己也没有解开的办法。

## 六、路线选择：为什么不做 GitHub 登录

设想过「App 内 GitHub 登录 → 学习数据存到用户自己的 Gist」，评估后**否决**。
技术上链路是通的（备份已是加密文本，Gist 就是存一段文本的地方；规模也够：
2834 词 → 180KB JSON / 加密后 241KB），但四个问题让它不适合普通用户：

| 问题 | 说明 |
|---|---|
| **client_secret 藏不住** | GitHub OAuth 换 token **必须**带 `client_secret`。纯客户端 App 里放 secret 等于公开 —— 反编译 APK 就能拿到，拿到的人可以冒充本 App。出路只有 Device Flow（体验割裂）、用户自填 PAT（门槛高）、或搭后端（那就回到本文主线了） |
| **门槛** | 用户要注册 GitHub、手动生成 PAT。为了背单词走这一步，会劝退九成用户 |
| **国内访问不稳** | 版本自检一天一次还能忍；同步是用户主动触发的操作，卡住一次体验就很差 |
| **两个口令不是一回事** | GitHub 管"存到哪"，加密口令管"看不看得懂"。只靠私有 Gist 的话数据对 GitHub 是明文 → 换设备实际要输两个东西，用户更容易搞混 |

**结论**：面向普通用户时，GitHub 不是合适的存储后端。

## 七、手动同步：能力其实已经有了

现在的「导出 → 分享面板 → 另一台导入」**就是手动同步**，零开发、零门槛、国内随便用。

**家底（别重复造）**：

- `utils/backup.js` —— PBKDF2 + HMAC-SHA256 加密，可选密码档
- `utils/backup-io.js` —— 写文件 + 系统分享面板（已含 Quick Share / 小米互传 /
  华为分享 / OPPO / vivo 互传，四家互通，60~140MB/s）
- 设置页 —— 导出三选一、「上次备份 X 月 X 日」、分享引导文案

**短板不是传输能力，是这两条**：

1. **用户记不起来。** 换手机是一次性场景，平时没人会想"该备份了"。
   现有「上次备份」是**被动显示**的 —— 不进设置页就永远看不到。
2. **步骤有 5 步。** 导出 → 选微信 → 发给自己 → 新手机保存 → App 导入。理想是点一下。

> 顺带一条零成本的兜底：**手机厂商云备份**（华为云 / 小米云 / OPPO / vivo 云）
> 能整份带走 App 数据，用户开了就不用管。
> 依赖 manifest 的 `allowBackup`（Android 默认 true，`manifest.json` 目前未显式配置，
> 值得确认一次）。

## 八、想压成"点一下"：同步码 + 后端

要做成 App 内一键同步，就绕不开一个放数据的地方。这是唯一不能省的。

**免账号设计 —— 同步码**：

```
用户自设一个码 → 用它派生密钥加密整份数据 → 存后端
                                          ↓
              另一台设备输同一个码 → 拉取 → 解密 → 导入
```

- 不用注册、不用邮箱验证、不用短信（短信要钱）
- 心智模型和现有备份加密口令一致，用户不用学新概念
- 服务端存的是密文，它自己也没法解开
- ⚠️ **码丢了 = 数据取不回**，没有找回途径。这一点必须在 UI 上明确告知，
  并在首次设置时让用户确认一次（和"备份口令忘了就解不开"是同一个道理，但要说在前头）

**后端选型**：国内可访问的 Serverless（腾讯云函数 + COS），避开 GitHub 不稳的问题；
免费额度对个人项目足够。地址填进现有的设置 › 关于 › 服务器地址即可，
`services/api.js` 已经把"没填就降级为纯本地"这条路铺好了。

## 十、已知限制

- **wgt 推不了原生**：同步逻辑走 HTTP，wgt 能推；但要新增权限、原生模块、
  改图标 / 启动图 / 包名，必须发 APK。
- **换签名 = 换 App**：APK 换了证书，老用户必须先卸载，学习数据会丢。
  所以打包要**沿用原证书**（`Arona.keystore`），别顺手换。
- **GitHub API 未认证限 60 次/小时/IP**：版本自检已做 12 小时节流，够用。
  但 §六 已否决把用户数据放 GitHub。
- **同步码不可找回**：后端只有密文，码丢了谁也解不开。必须前置告知用户。
- **手动同步不做自动合并**：两条设备都学了词时由用户选"以哪份为准"，
  不做智能合并 —— 不做就不会算错，符合铁律 3。
