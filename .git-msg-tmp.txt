扩充本地默认单词库：新增 data/word-senses.js（3316 条一词多义全量释义）+ 补收 218 词

用户原话：「最好还是本地多添加一些单词的缓存，能齐全尽量齐全……并且许多单词
有一词多义，尽量地把默认单词库都丰富一遍。注意说的是单词库，不是词书。」

一、为什么另开一张表，而不是放宽 MAX_MEAN
   词书共享表（lexicon-data.js）的一行 = 一张**背诵卡**，释义只有 20 字上限，
   于是 light（源表 22 义）、hard（14 义）、note（12 义）这类多义词
   在界面上永远只看得到前四五个 —— 这正是用户反馈的「一词多义显示不全」。
   而「背诵卡要一眼扫完」要求释义短。两个消费方的需求冲突，所以拆成两份：
     · 共享表 / 补充表：短版，给背诵卡与搜索列表
     · data/word-senses.js：不截断的长版，只给查词 / 点读 / 词条页
   buildEntry() 参数化为 (glosses, cap, maxSenses, stat, relaxed)，
   旧调用点不传参 → 默认 20，产物字节级不变。

二、为什么清洗规则要分「严格档 / 词典档」两档
   词典档修掉了三处误杀（228 条被剔光的候选词 → 10 条）：
     1. 源表大量使用「， 」「； 」这种标点后加空格的排版，残留空格过不了
        SENSE_OK，writer / cute / alright / anymore / furry / specifically
        这类再普通不过的词被整条丢弃；
     2. SENSE_JUNK 里写的是裸 `棒球`（本意 `棒球术语`），
        结果 baseball 唯一义项被判 junk → 本地词典查不到 baseball；
     3. 兜底逻辑取 splitSenses(...)[0]，而 stripPos 会把行首词性换成 SEP，
        第一个片段恒为空串 → socks 这类词必然救不回来，改取第一个非空片段。
   严格档（含裸 `棒球` 的 SENSE_JUNK_LEGACY）继续喂共享表，
   就是为了冻结行成员：洗宽规则会让原本没释义的词变得有释义 →
   多出约 49 行 → 行号位移 → 老用户已背记录错位且不报错。

三、规模变化
   查词补充表：2794 → 3012 条（+218，来自上面三处修复 + 日常短词表）
   完整义项表：新增 3316 条
